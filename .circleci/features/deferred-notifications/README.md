# Deferred native notification permission (candidate)

Target Brave1.100.58 bd6d26d1bced03c17a98baa86d2cd3425d543d1b, Chromium158.0.8127.42 52bdd21723d5db0c9ab11716d38feac74828cf84. Exact upstream controller/coordinator fixtures are hash-recorded. Applies only two existing Java owners, no new GN target.

Welcome owns default-on toggle and atomic persistent intent in dedicated `sandium_notifications`: enabled/defaulttrue, setup_completed, request_pending, request_attempted. Completion must not continue if disk commit fails. This helper does not grant permission and enabled does not mean Android permission is granted.

Controller suppresses automatic startup requests and contextual requests before completed setup/while pending or while toggle disabled. Coordinator waits for a resumed, focused, interactable normal native NTP, browsing layout, attached/shown/nonzero homepage view and no modal. It registers Android frame-commit then posts back to UI and rechecks current tab and view before calling the native controller. Existing Android eligibility, prior requests/denial, API/demo exclusions, field-trial limits and tracker cooldown remain. Only this first eligible handshake converts initial rationale into direct native OS choice. It does not reset OS or Chromium denial history.

Pending survives a welcome-triggered restart. Before attempting any OS request it synchronously commits pending=false and attempted=true. A failed commit never dispatches an OS request. Android SharedPreferences may already have changed its in-process state even when commit returns false; a later activity in that process is not guaranteed to retry. This deliberately guarantees at-most-once attempt, not exactly-once display: process death after the commit but before OS dispatch can lose that attempt. A suppressed native eligibility/cooldown also does not produce a later surprise startup prompt. No first-launch notification is posted.

Frame commit demonstrates a rendered frame submitted to the swap chain, not physical screen presentation. Software-only rendering has no frame-commit guarantee and is conservatively excluded; normal hardware-accelerated Android UI is expected.
